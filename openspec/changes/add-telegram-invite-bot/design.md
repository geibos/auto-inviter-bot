# Design: Telegram Invite Bot

## Context

Проект с нуля (репозиторий пуст). Бот выдаёт персональные одноразовые invite-ссылки в закрытую Telegram-группу через inline-режим; реестр «позывной + @username» ведут операторы в личке бота.

Ключевые факты из исследования (Telegram Bot API 10.0, май 2026; проверено по core.telegram.org/bots/api):

- `InlineQuery` содержит только `id, from, query, offset, chat_type, location`. **Chat id и идентичность собеседника недоступны** — ни одна версия API (включая 7.x–10.0) этого не добавила. `ChosenInlineResult` тоже не содержит chat id.
- `createChatInviteLink`: `name` 0–32 символа, `member_limit` 1–99999, `creates_join_request` несовместим с `member_limit`. Возвращает `ChatInviteLink`. Требуется админство с правом `can_invite_users`.
- `member_limit=1` означает «не более одного участника одновременно по этой ссылке»: если вступивший выйдет, ссылка снова рабочая. Явно это нигде не задокументировано; подтверждено эмпирическим тестом (bugs.telegram.org/c/2745, с шагами воспроизведения; Telegram закрыл репорт как intended behavior) и формулировкой Bot API («members of the chat **simultaneously**»). Клиентские счётчики (tdesktop/TDLib `usage`) монотонны, но лишь отображают серверные значения и поведение сервера не опровергают. Уверенность — средняя (единственный тест 2021 года). Вывод: строгая одноразовость достигается **только** отзывом ссылки после вступления.
- `ChatMemberUpdated.invite_link` сообщает, по какой ссылке вступил пользователь. Апдейт `chat_member` **не входит** в default-набор — его надо явно указать в `allowed_updates`, и бот должен быть админом.
- Документированного лимита активных ссылок на админа нет (анекдотически ~50 в UI). «Each administrator generates their own invite links. Bots can't use invite links generated by other administrators».
- teloxide 0.17.0 (июль 2025, Bot API 9.1) покрывает всё нужное: `Update::filter_inline_query()`, `answer_inline_query`, `create_chat_invite_link` с `.name()/.member_limit()`, `Update::filter_chat_member()`, `Update::filter_my_chat_member()`. Dispatcher автоматически выводит `allowed_updates` из дерева хендлеров (`hint_allowed_updates`). Все используемые методы существуют с Bot API 5.x — отставание teloxide от свежайшего API не мешает.

Деплой: `sobieg@10.216.0.11`, директория `~/full_server`, Docker. Требование: настройка одним `BOT_TOKEN`.

## Goals / Non-Goals

**Goals:**

- Оператор за два действия выдаёт кандидату персональную ссылку: `@bot <позывной>` → tap.
- В админском списке invite-ссылок группы каждая ссылка подписана позывным.
- Видно, кто вступил, по какой ссылке и когда; использованная ссылка отзывается.
- Zero-config: токен — единственная обязательная настройка; группа и операторы определяются автоматически.
- Состояние переживает рестарты контейнера.

**Non-Goals:**

- Несколько групп в v1 (схема БД готова, UX — нет).
- Webhook-режим, входящие порты, TLS-терминация.
- Резолвинг @username → user id (Bot API этого не умеет); username — метаданные для оператора.
- Авто-кик/модерация вступивших, не входящих в реестр.
- Web-интерфейс, Google Sheets-синхронизация.

## Decisions

### D1. Стек: Rust + teloxide 0.17 + sqlx/SQLite

Функционального разрыва нет (проверено по docs.rs: `CreateChatInviteLink` имеет поля `name`, `member_limit`, `expire_date`, `creates_join_request`). Статический musl-бинарь даёт образ ~7 МБ (scratch) против ~55 МБ (grammY/node-alpine) и ~120–200 МБ (aiogram/python-slim).
**Альтернативы**: grammY — преимущество same-day-покрытия Bot API не нужно (все фичи из API 5.x); aiogram — быстрее писать, но тяжелее образ и нет преимущества по функциям. Pin teloxide на `0.17` (частые BC-ломки между минорами).

### D2. Inline-UX: позывной — аргумент запроса

Вынужденно: inline-бот не знает чат (см. Context). Оператор набирает `@bot <позывной>` в любом чате, бот отвечает карточками-кандидатами (substring-поиск). `is_personal=true` и `cache_time=0..5` — результаты зависят от прав вызывающего и состояния реестра. Пустой запрос → первые N невступивших записей.

### D3. Жизненный цикл ссылки: одна активная на запись, eager + get-or-create

Инвариант: **не более одной активной ссылки на запись реестра** (partial unique index). Создание:

1. eager — при добавлении записи, если группа привязана (требование «бот под каждого из вгруженных генерирует ссылку»);
2. lazily get-or-create — при inline-запросе (на случай, если запись добавили до привязки группы).

Inline-запросы прилетают на каждый кейстроук — создавать ссылку на запрос нельзя; get-or-create с reuse решает это: худший случай — одна ссылка на запись за всё время. Параметры: `member_limit=1`, `name=<позывной>` (обрезка до 32 символов). После вступления ссылка отзывается (`revokeChatInviteLink`) — закрывает дыру «вступил и вышел — слот освободился». `/reissue <позывной>` — явный перевыпуск (отзыв старой + новая).
**Альтернатива** (создавать ссылку только в момент выбора результата через `chosen_inline_result`) отвергнута: содержимое сообщения фиксируется при ответе на inline-запрос, после выбора его не подменить.

### D4. Авторизация: админы привязанной группы

Оператор = `getChatMember(bound_chat, from.id).status ∈ {creator, administrator}`. Кэш результата на 60 с (HashMap + Instant за Mutex; без внешних зависимостей) — getChatMember на каждый кейстроук недопустим. Не-операторы: команды → вежливый отказ, inline → пустой ответ (бот не раскрывает своё назначение).
**Альтернативы**: whitelist в env (ломает zero-config), «первый /start — владелец» (хрупко, race при первом запуске).

### D5. Хранение: sqlx + SQLite, не teloxide dialogue storage

Dialogue storage teloxide хранит только FSM-состояние диалога по ключу чата; нужны произвольные таблицы. `Pool<Sqlite>` инжектится через `dptree::deps![]`, миграции — `sqlx::migrate!` при старте. Файл БД: `/data/bot.db` (env `DATABASE_PATH` для переопределения, дефолт работает из коробки).

Схема (v1, с заделом на мультигруппу):

```sql
chats(id INTEGER PK, tg_chat_id INTEGER UNIQUE, title TEXT, is_active INTEGER, bound_at TEXT);
roster(id INTEGER PK, chat_id INTEGER REFERENCES chats,
       callsign TEXT COLLATE NOCASE, username TEXT NULL,
       created_by INTEGER, created_at TEXT,
       joined_tg_user_id INTEGER NULL, joined_username TEXT NULL, joined_at TEXT NULL,
       UNIQUE(chat_id, callsign));
invite_links(id INTEGER PK, roster_id INTEGER REFERENCES roster,
             invite_link TEXT UNIQUE, name TEXT, created_at TEXT,
             revoked_at TEXT NULL, used_at TEXT NULL);
-- инвариант: уникальный partial-index на invite_links(roster_id) WHERE revoked_at IS NULL AND used_at IS NULL
```

Статус записи — производный: `joined_at` → «вступил»; активная ссылка есть → «выдана»; иначе «ожидает».

### D6. Привязка группы: через `my_chat_member`

Бот привязывается к первой группе, где получил статус `administrator` с `can_invite_users=true`: пишет подтверждение в группу и сохраняет привязку. Добавлен без прав → пишет инструкцию («повысьте до админа с правом Invite Users») и ждёт повышения. Добавлен во вторую группу при живой привязке → сообщение «уже обслуживаю другую группу» + `leaveChat`. Потеря прав/удаление из привязанной группы → привязка помечается неактивной (данные сохраняются), `/status` это показывает; восстановление прав реактивирует.

### D7. Bulk-import: любое некомандное сообщение оператора в личке

Каждая строка — `позывной [@username]`; разделители: пробелы, табы, `;`, `,`. Позывной — первый токен (без пробелов), `@` у username опционален. Ответ — сводка: добавлено / пропущено-дубликаты / некорректные строки (с номерами). Это покрывает и «вставил список из 50 строк», и быстрые одиночные добавления без команды. `/add <позывной> [@username]` остаётся как явная форма.
Парсер — чистая функция, покрывается unit-тестами.

### D8. Long polling, не webhook

Zero-config: нет портов, TLS, домена; контейнер делает только исходящие соединения. `chat_member` в `allowed_updates` teloxide выставит сам по дереву хендлеров, но при старте дополнительно логируем фактический набор (известны edge cases автодетекта).

### D9. Тестируемость: тонкие хендлеры, чистая логика

Вся логика, не требующая Bot API (парсер импорта, поиск по реестру, выбор/инвариант ссылок, форматирование `/list`), — чистые функции и функции над `Pool<Sqlite>`; unit/integration-тесты на sqlite in-memory. Хендлеры teloxide — тонкие обёртки. E2E — вручную с тестовым ботом и тестовой группой (чек-лист в tasks.md).

### D11. Создание налету: карточка + chosen_inline_result (без спецсинтаксиса)

Контент inline-сообщения фиксируется в момент ответа, а запросы летят на каждый кейстроук — создавать записи в момент запроса нельзя: набор «Новичок» породил бы записи «Н», «Но», «Нов»… Первая итерация решала это суффиксом «+»; по фидбеку оператора заменена на карточный флоу: карточки «Создать „X"» (при отсутствии точного совпадения) и «Новая ссылка» (первая при пустом запросе) отправляют сообщение-заглушку с inline-клавиатурой; `ChosenInlineResult.inline_message_id` (доступен только при наличии клавиатуры) позволяет после создания записи и ссылки отредактировать сообщение через `editMessageText`. Создание происходит строго по явному выбору карточки — промежуточные и повторные запросы ничего не создают, дебаунс не нужен.

Цена решения: `/setinlinefeedback` = Enabled у BotFather обязателен, иначе `chosen_inline_result` не приходит и заглушка не обновляется (зафиксировано в README/troubleshooting; заглушка «⏳ Готовлю приглашение…» делает проблему видимой). Повторный выбор именной карточки идемпотентен (Duplicate → reuse активной ссылки); каждый выбор гостевой карточки осознанно создаёт нового «Гость-N». «Совсем без записи» нельзя: на записи держатся имя ссылки в группе, join-tracking и инвариант одной активной ссылки. Декоративная кнопка заглушки — callback с пустым ответом (URL-кнопка потребовала бы тип Url и лишнюю зависимость).

### D12. Нейтральный текст приглашения и отображение личности

Текст приглашения, видимый кандидату, не содержит внутренних идентификаторов (позывной, «Гость-N») — нейтральное «Личное приглашение в группу: <ссылка>». Имя кандидата в момент выдачи недоступно принципиально (inline не знает чат, D2). После вступления личность известна из `chat_member` (`User.first_name/last_name/username`) — сохраняется в `roster.joined_name` (миграция 0002) и показывается оператору везде как «Имя Фамилия (@username)»: в `/list` и в описаниях inline-карточек вступивших. До вступления идентификатор записи — только позывной/«Гость-N» (другого нет).

### D10. Деплой: docker-compose в `~/full_server`

Multi-stage Dockerfile: `rust:alpine` (musl, static) → `scratch` + CA-сертификаты. Compose: `restart: unless-stopped`, `env_file: .env` (только `BOT_TOKEN`), volume `./data:/data`. Доставка: rsync исходников на сервер + `docker compose up -d --build` (на сервере есть Docker). Rollback: предыдущий образ; данные в volume не затрагиваются.

## Risks / Trade-offs

- [Видимость `name` ссылки в админском UI клиентов не специфицирована в Bot API docs] → практически отображается; проверить на живой тестовой группе на этапе верификации. Дублирующий канал: `/list` показывает соответствие позывной↔ссылка↔вступивший.
- [`member_limit=1` не строго одноразовая: выход освобождает слот (подтверждено, см. Context)] → отзыв ссылки сразу после фиксации вступления (D3); revoke ретраить до подтверждения, при неудаче — лог + сообщение операторам. Residual-окно: между join и revoke (бот офлайн/лагает) вышедший освобождает слот для второго входа; при необходимости закрывается коротким `expire_date` на ссылке (в v1 не делаем, опция на будущее).
- [Кандидат может переслать ссылку третьему лицу] → ущерб ограничен одним вступлением; join-tracking пишет фактический `user_id`/`username` вступившего, расхождение с реестром видно в `/list`.
- [Анекдотический предел ~50 активных ссылок в UI] → отзываем использованные; для больших реестров (>50 невступивших) поведение проверить; документированного лимита API нет.
- [`chat_member`-апдейты не приходят (нет админства / allowed_updates)] → лог фактических allowed_updates при старте, диагностика в `/status` («права: ок/нет»).
- [Кэш операторов 60 с: разжалованный админ сохраняет доступ до минуты] → принято осознанно; TTL — константа в коде.
- [teloxide BC-ломки между минорами] → pin `=0.17`-семейства, обновления только осознанные.
- [SQLite single-writer] → нагрузка крошечная (единицы запросов/с максимум), не проблема.

## Migration Plan

1. Локально: `cargo test`, запуск с тестовым токеном, ручная проверка по чек-листу (привязка, импорт, inline, вступление).
2. Сервер: rsync проекта в `~/full_server/auto-inviter-bot`, `.env` с боевым токеном, `docker compose up -d --build`.
3. BotFather: `/setinline` (включить inline-режим, задать placeholder), опционально `/setinlinefeedback`.
4. Добавить бота в боевую группу админом с правом «Invite Users».
5. Rollback: `docker compose down` + предыдущий образ; volume с БД сохраняется.

## Open Questions

- Подтвердить на живой группе отображение имени ссылки в «Invite Links» (этап верификации; API-доки этого не специфицируют — см. Risks).
- Поведение при >50 активных ссылок — проверить, если реестр вырастет (не блокирует v1).
